## 2026-11-11：服务断线、重启后白屏排查记录

**现场现象与证据**：用户报告长时间未使用后服务断开，点击「重新启动工作台」后白屏。旧日志中一次 `ticket-minted` 后没有相邻的 `ticket-redeemed`；不能仅凭此断定事件对应那次点击，也不能断言白屏的唯一根因。

**代码层发现与教训**：

- 旧故障按钮跳到回环调试地址 `/editor`，该入口只是签发已有代理地址并重定向，不负责启动失联的 Studio。应由 iframe 通知外层面板重新 bootstrap；消息必须校验来源 origin、当前 iframe 的 `contentWindow` 和协议版本。
- 旧 `running` 是内存里的 `ready` 位，启动后上游失联也可能仍为真。现在通过受限的本地 `/api/health` 检查实际实例，失败后保留清理句柄，后续启动清理旧代理及实例，再重建；不得以单个健康位推断 iframe 或其凭证也有效。
- 旧白屏检测只关注首次启动；iframe 后续导航到错误页时可能没有提示。现在导航重新计时，诊断提示由外层显示并保留 iframe；注入脚本在页面真正渲染后补发 boot，避免首次 boot 早于慢加载或 iframe load。重启/刷新会丢失未保存编辑，应事先提醒。
- 桌面 `dsh-app://app` 的相对 `/api/...` 不到 Host，不能把它返回的 404 当成 Studio 断线。HTTP Web 和桌面协议要分别验证。
- 日志应记录 `studio-health`、`bootstrap-start`/`bootstrap-finish`/`bootstrap-failed` 的状态、阶段、耗时及安全错误类别；不要写上游原始异常、票据、密钥、完整凭证 URL 或项目路径。票据发出不等于页面已加载。

**验证边界**：本次 `npm run build` 成功；`node --test tests/*.test.mjs` 为 192 项、191 通过、1 跳过。模拟测试覆盖上游断开恢复、清理失败、并发、面板消息来源和导航超时；**尚未在真实 GUI 验证断线后恢复或白屏提示**，不可写成真机已修好。

**重载注意**：插件管理器 disable/enable 均返回 `restart-required`（`unmanaged-plugin`），与此同时日志出现新的 `host-start` 和 `studio-warm`。这只能说明观察到 Host 重建，不证明管理器要求的全部变更已应用；需向用户如实报告并按提示完整重启 DSH，再刷新页面和验证 GUI。

## 二、主要决策（附理由）

### D1 独立仓分发，不是工作台的一个分支

- **决定**：`dsh-openfilm` 作为独立插件仓，远程 `NewbieCheng/dsh-openfilm`，`main` 分支。
- **理由**：工作台仓 `不加班智能团-desktop` 历史长、耦合多，插件需要可分发的边界（`package.json` 的 `files` 白名单 + `dsh.bundle.patch` + `dsh.client`）。
- **代价**：两边代码不能直接共享；`vendor/film-doc.mjs` 只能是上游副本。
- **约束**：只推本仓；工作台的 `vendor/dsh` 只读。

### D2 面板挂 `shell.overlay`，`main` 只放占位

- **决定**：真面板渲染在 `shell.overlay`，`main` 放一个只上报矩形/选中状态的 `div`；面板用 `position:fixed` 跟随占位矩形。
- **理由**：`main` 会在切页时卸载，导致 iframe 里的 Studio 整个重载、丢失编辑状态。`shell.overlay` 在整帧生命周期内常驻。
- **代价**：需要自己同步布局（`resize` + 500ms 轮询取矩形），不能依赖 shell 的布局内部结构。
- **证据**：`src/panel-keepalive.mjs`、`src/studio-entry.js`；0.3.0 提交"面板常驻，切换页面不再重载 Studio"。

### D3 默认用官方桌面 shell，DSH 对话列作为回退

- **决定**：默认 `officialShell: true`（`vendor/official-shell/ui` 整页官方界面，含它自己的对话列）；`NO996_OPENFILM_DSH_CHAT=1` 退回内嵌 DSH 对话列。
- **理由**：用户要的是"官方工作台完整保留"，而不是自己拼一个近似界面；DSH 只做后端。
- **代价**：shell 是上游构建产物，改动必须走 `scripts/build-official-shell.mjs` 重生成 manifest（逐文件 sha256 校验）；版本与 commit 和 npm 依赖必须同步。

### D4 浏览器只看到代理端口，Studio 密钥不出 Host

- **决定**：`startStudio({port:0})` 只 bind 临时端口；浏览器访问 `47822` 的代理；代理内部带 `x-studio-key` 转发。
- **理由**：密钥一旦进浏览器，任何页面脚本都能直接操作 Studio。
- **代价**：WebSocket 帧要改写 Origin、要拦 `key`/`ticket` 出现在 URL 的情况（`studio-proxy.mjs`）。

### D5 固定端口 47822 / 47821

- **决定**：编辑器代理固定 47822，模板控制台固定 47821，都可用环境变量覆盖（`NO996_OPENFILM_EDITOR_PORT` / `NO996_OPENFILM_DEBUG_PORT`，后者设 `0` 关闭）。
- **理由**：给用户一个可手输的稳定地址（右侧浏览器没有 DSH cookie，所以控制台由 Host 代做 Studio 工作）。
- **代价**：端口冲突时会直接失败；调试控制台是额外的攻击面，因此只本机、只白名单、只回项目 ID。

### D6 模板复制"独占创建 + 失败不删"

- **决定**：`installTemplate` 用独占创建目录，拒符号链接，限制 4000 文件 / 64 MiB；注册失败**保留目录**并报"结果不确定"。
- **理由**：一旦 `openProject` 可能已提交，删除就可能删掉一个已注册项目；宁可让用户确认。
- **配套**：面板收到"不确定"后暂停重复创建，提示先打开已有项目检查。

### D7 对话失败分为"已归因"与"未归因"

- **决定**：已归因失败（明确结束）→ 可重试；未归因失败（请求可能已受理但回执丢失）→ 锁项目并要求人工确认，不自动重发。
- **理由**：自动重发可能造成重复执行；永久锁死又会卡住用户。0.3.1 修的是后者。
- **历史教训**：曾经把未归因失败当永久失败，项目被锁死。

### D8 增量按 index 去重，允许跳跃与中途接管

- **决定**：放弃严格顺序规则。
- **理由**：严格顺序会丢弃实时增量，用户看不到思考和回复（0.3.2）；但反过来把"正常 unchanged"当流失效也是错（0.3.3）。

### D9 诊断先埋记录，再改翻译层

- **决定**：0.3.4 每轮写 `%TEMP%\dsh-openfilm-frames.jsonl`（覆盖、文本截断 200 字符）。
- **理由**：`official-agent-events.mjs` 的 bug 全部是"真实分片类型名与假设不符"，只能看真帧，不能猜形状。

### D10 不把实验代码接进主线

- **决定**：`src/project-core.mjs`（协作锁 / 文件系统实验）保持未注册；`src/client-entry.js`（早期工作区浏览 UI）不在构建链里。
- **理由**：它的锁不是对外部写者的原子 CAS，Node 文件系统也不是 DSH 沙箱的替代品。接上去等于给用户一个"看起来有保障、实际没有"的边界。

### D11 归档走 DSH 自己的集合，不建第二份（0.4.0）

- **决定**：归档状态只从 `workspaceController.follow` 读，写只调 `archiveSession/unarchiveSession`；项目绑定保留归档会话，`rebind` 才换会话。
- **理由**：归档集合同时是 `agent/pre-step` 门禁的数据源，自建一份必然与 DSH 侧边栏分叉，且分叉表现为"面板里还能发消息、但每轮 20 毫秒被 blocked"。
- **代价**：`workspaceController` 缺席的 profile 只能报告 `available:false`，不能假装知道。

### D12 归档项目再发消息：明确拒绝 + 两个按钮（0.4.0，A1）

- **决定**：不自动取消归档、不自动换绑；面板横幅给「恢复会话」「新建会话」。
- **理由**：两者都会改写用户的会话身份，且归档常常是用户主动做的；自动动作会让人分不清"我归档了但它还在跑"。
- **代价**：多一次点击。

### D13 工具卡片信息量：名称 + 参数摘要 + 结果首 500 字（0.4.0，C1）

- **决定**：`tool_call` 带 `title/kind/rawInput`，`tool_call_update` 带 `status/content/rawOutput`；单条截断 8 KiB、参数 4 KiB。
- **理由**：用户要看"模型在干什么"；只显示名称等于没显示。截断是因为工具结果可能含私有路径与超长日志。
- **代价**：长结果不可全文阅读（需要时去 DSH 会话详情看）。

## 四、踩坑记录（都真实发生过）

1. **严格顺序 → 丢增量**：用户看不到思考和正文。改为 index 去重 + 允许跳跃。
2. **反向过度纠正 → 把 unchanged 当流失效**：正常对话回 503。0.3.3 修。
3. **未归因失败当永久失败**：项目被锁死没法再发消息。现在可重试。
4. **新会话没模型**：首条消息必失败。现在建会话后一次性采用宿主默认模型，且发送不再覆盖用户选的模型。
5. **预设缺一个必填配置**：`tool-fs-search.sampleOverCapGlobResults` 缺失导致整个预设 invalid config。`cordis.patch.yml` 里留了注释。
6. **手改官方 shell 的 ui 不更新 manifest**：启动即 `OFFICIAL_SHELL_UNAVAILABLE`。
7. **子智能体任务粒度太大**：连续两次整体失败。现在拆成单点任务逐个验证。
8. **"报漂亮但没验证"**：用户明确反感。所有"完成"必须有界面证据。

## 五、热加载纪要（最常被问）

- **一句话**：本插件不是热加载的，但也不需要重装——改客户端 `npm run build` + 刷新，改 Host 重启 DSH，改模板下一次请求就生效。
- **为什么不用重装** ✅：`~/.dsh/profiles/desktop/node_modules/dsh-openfilm` 是指向 `F:\Dev\Desktop-Projects\dsh-openfilm` 的链接（本次 `readlink` 实测），磁盘文件就是安装文件。
- **为什么改完还得重启/刷新** ✅：Node ESM 模块每进程只求值一次；浏览器 bundle 在页面加载时取一次。仓库里没有 watcher（`package.json` 只有 `build`）。
- **HMR 的边界**：DSH 客户端插件热替换只在使用 `pnpm run dev:web` 从同一 checkout 起服务时成立；本插件是已安装的第三方包，不在这条链路上。**不要假设"改完自动热更"**。
- **代价**：刷新页面会重载 iframe，面板里未保存的编辑丢；重启 Host 会重建 Studio 子进程与代理，但会话和项目不受影响。
- **最容易犯的错**：忘了 `npm run build` 就刷新 → 看到旧 bundle，然后去怀疑别处。

详细矩阵见 `DEVELOPMENT.md` §8、`../AGENTS.md` §4。

## 八、0.7.0 第 1 步：观测层（已接线）

目标：把"右边什么都没有"从推测变成可判定——拆成 **① DSH 没产出 → ② 桥接没发出 → ③ 发出但页面没收/没画**。

### 已接线

| 环节 | 落地 |
|---|---|
| ① DSH 产出 | `%TEMP%\dsh-openfilm-frames.jsonl`（既有，每轮覆盖写） |
| ② 桥接发出 | `src/bridge-trace.mjs`：计数 `emitted/accepted/refused`、`sessionUpdate` 分布、最近 40 条 envelope；在 `studio-controller` 里包住 `emit`，publish 的返回值就是"有没有活着的面板流接收" |
| ③ 页面收到 | `official-facade` 在每轮 `prompt` 结束时通过新通道 `agent:trace` 上报 `{seen, kinds}`；Host 侧 `bridgeTrace.panel()` 校验后存 |
| 读取 | `POST /api/no996-openfilm/diagnose` 的 **`bridge`** 段 |

`bridge` 只是计数与 `sessionUpdate` 名字（≤200 字符、名字白名单 `/^[a-z_]{1,40}$/`），不记模型文本、不记路径、不记 key。

### 静态已证的根因（不需要跑也能确认）

1. `src/official-agent-events.mjs:49-59` 的 `toolCallEvent()` 恒发 `kind:'other'`，而官方壳子的动作词典按 `read/edit/search/execute/fetch` 选择中文文案（`正在读取文件` / `正在运行命令` …），落到默认分支就只有「正在处理」。
2. 同一个函数把 `rawInput` 序列化成**字符串**，壳子取细节处是 `typeof n === 'object' ? n : {}`，于是文件名、命令行全部丢失。
3. 壳子只在 `tool_call_update` 的 `completed`/`failed` 改状态，中间态不画；所以"进度"要靠新的 `tool_call` + `plan` + `notice` 表达。
4. **仍待真机确认的一条**：事件是否真的抵达页面（即 ③）。在 §1.4 的判定表里，`panel.seen > 0` 且右侧空白 = 壳子不画（第 4 步修）；`refused > 0` = 事件流没接上（另一类 bug）。
